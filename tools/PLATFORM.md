# FTH Reporting Platform — architecture

Two surfaces on the static site, one calculation core, one confidentiality layer.
No server code: nginx serves files, every computation and every cryptographic operation runs
in the browser (WebCrypto). `/tools/` is blocked by nginx: this file is not public.

```

   magic-byte check)                      open .fthpkg / .fthwork / ОСВ
```

## Files
| File | Role |
|---|---|

| `js/fth/vault.js` | Crypto: key set, sealed envelopes (ECDH P-384 + HKDF-SHA-256 + AES-256-GCM), signed releases (ECDSA P-256, PBKDF2-SHA-256 600k + AES-256-GCM). |

## Security model
- **No data path to any server.** The pages make no request after load (tested), store nothing
  (no localStorage/IndexedDB), CSP `connect-src 'self'` + `script-src 'self'`.
- **Upload**: size limit, real type by magic bytes (OLE2/ZIP), SheetJS without formulas,
  macros or styles; at most 10 sheets, 20 000 rows; text cells only in exports (no formula injection).
- **Client → FTH**: sealed to the FTH public key; header (kind, key id) authenticated as AAD.
- **Access split** is cryptographic: the workspace page is public code but opens nothing without
  the private key; the client only ever receives a release holding statement figures (never TB,
  mapping or journals), signed by FTH and verified by the portal.
- **Private key**: `.fthkey`, encrypted with a passphrase, kept off the web server
  (current set: `/home/vadim/fth-keys/`, key id in `data/fth-keys.js`). Keep two offline copies.
  Rotation: workspace → "New key set" or `node tools/fth-keygen.mjs <dir>`; keep old key files
  to open packages sealed before the rotation.

## Excel model audit (15/11/2026)
`tools/AUDIT-excel-model.md` lists the errors found in the Excel workbook and its scripts (cash flow, balance, P&L, equity,
IFRS 15/16, IAS 21/38/12, non-idempotent pipeline). The platform does not reuse that logic: cash flow, current tax, IAS 38
and IFRS 15 are re-implemented in `core.js` with tests (journals must balance, cash flow must reconcile, current tax from the
tax base, deferred tax computed once by the IAS 12 calculator). The Excel scripts were not patched (Windows COM, local paths).

## Accounting rules worth knowing
- Model 2.0 corrects the Excel Mapping sheet (3711, 377, 352, 471, 235, 91, 422/424/425, 83x, 7/79x)
  and adds missing chart accounts (38, 39, 43, 48, 53, 55, 62, 67, 69, 72, 73…). List with reasons
  in `data/ifrs-model.js`, shown in the workspace ("FTH model").
- A TB closed through 79 is rebuilt from turnovers and **reconciled to the movement of account 44**;
  the gap (VAT debited to 70, reversals, dividends) is a check, cleared by an "extraction" journal.
- Journals post on IFRS categories, never on chart accounts. Current scope: closing + P&L (flows to
  retained earnings); opening scope: opening and closing balances, no P&L.
- Nothing is labelled IFRS-compliant: portal output is "preliminary"; releases carry a disclaimer
  (no notes, no cash flow statement, not audited).

## Roadmap to a full IFRS transformation platform
1. **Server tier** (needs sudo on the VPS or a managed host): accounts with roles
   (client / preparer / reviewer / partner), MFA, per-engagement storage of the same encrypted
   envelopes (server stores ciphertext only), notifications. The JSON schemas here (`client-package`,
   `working-file` v1, `release`) are the API payloads: no rework of the core.
2. ~~Cash flow statement~~ done (15/11/2026): indirect, derived from the IFRS balance sheet so it reconciles to cash by construction
   (`cashFlow` in core.js, workspace tab "Cash flows", check `cashflow`). Not in the client release yet. Next: direct-method analytics
   from the cash accounts (ОСВ по рахунку 31) to replace the indirect classification of interest, tax and non-cash items.
3. Comparatives and IFRS 1 first-time adoption (opening-balance journals already supported).
4. Notes and disclosure checklist; IFRS 18 presentation (2027).
5. Multi-entity consolidation (IFRS 10), multi-currency presentation (IAS 21).
6. XBRL (ESEF) tagging of the released statements.
